## 1. Общее описание

### 1.1. Постановка

Нужен UI для работы с **рестриктивными списками** разных типов (МВК, Террористы и др.). Пользователь загружает файл (как правило Excel/CSV). Сервис передаёт файл **as is** (побайтово на удалённую папку) и параллельно публикует сообщение в **RabbitMQ** для уведомления внешнего сервиса парсинга. Содержимое файла UI **не парсит и не просматривает** — только метаданные загрузки (тип списка от оператора, имя, расширение, размер).

Если парсер не может разобрать отдельные поля, он записывает кейс в **БД Restrict**, отправляет пользователю письмо со ссылкой. По ссылке открывается страница обработки ошибок: UI читает данные из БД, пользователь дополняет/исправляет поля, UI сохраняет результат в БД.

### 1.2. Цель

Дать оператору понятный контур: **загрузка → асинхронная обработка** и **обработка ошибок** без HTTP API у парсера.

### 1.3. Связь с существующей системой

Репозиторий содержит каркас ASP.NET Core Razor Pages (`.NET 5`) — [`VTBL.Restrict.UI`](../VTBL.Restrict.UI). Парсер и почтовая рассылка — внешние системы.

### 1.4. Актёры

| Актёр | Роль |
| --- | --- |
| Оператор | Загружает файлы, выполняет обработку ошибок |
| VTBL.Restrict.UI | Приём файла, запись на шару, publish RMQ, UI обработки ошибок, работа с БД |
| Сервис парсинга | Читает файл, парсит, пишет кейсы в БД, инициирует письмо |
| RabbitMQ | Транспорт уведомлений о новой загрузке |
| Файловый сервер | Хранение входных файлов |
| СУБД Restrict | Справочники, кейсы обработки ошибок |

## 2. Юзер-кейсы

### UC-01. Загрузка файла рестриктивного списка

**Тип:** новый  
**Актёры:** Оператор, UI, файловый сервер, RabbitMQ  

**Предусловия:**
- Оператор аутентифицирован (механизм — отдельное решение в architecture; на MVP допускается конфиг/Windows auth/заглушка).
- Доступны удалённая папка и брокер RabbitMQ.
- В справочнике есть хотя бы один активный тип списка.

**Основной сценарий:**
1. Оператор открывает страницу загрузки.
2. Выбирает **тип списка** (например, МВК).
3. Перетаскивает файл в область DnD **или** нажимает «Загрузить» и выбирает файл с диска.
4. UI проверяет только оболочку: тип выбран; файл не пустой; расширение из белого списка (`.xlsx`, `.xls`, `.csv` — настраивается). Содержимое не читается.
5. UI формирует целевой путь (по правилам типа списка) и атомарно копирует поток файла **as is** на удалённую папку.
6. UI публикует сообщение в RabbitMQ (см. [integration-file-rmq.md](integration-file-rmq.md)), включая `listType`, `filePath`, `correlationId`.
7. UI показывает статус «Файл принят в обработку» (без ожидания парсинга).

**Альтернативы:**
- **A1. Файл отклонён валидацией:** шаг 4 → сообщение об ошибке, файл не пишется, RMQ не шлётся.
- **A2. Ошибка записи на шару:** шаг 5 → ошибка оператору, RMQ не шлётся; при частичной записи — политика очистки/идемпотентности (architecture).
- **A3. Ошибка publish RMQ после успешной записи файла:** файл остаётся; UI логирует инцидент и показывает ошибку с возможностью «повторить уведомление» (без повторной выкладки файла) либо процедуру поддержки — зафиксировать в architecture.
- **A4. Дубликат имени файла:** UI добавляет уникальный суффикс (`correlationId` / timestamp) по правилам типа.

**Постусловия:** файл на шаре; сообщение в RMQ (при успехе обоих шагов); оператор видит подтверждение.

**Критерии приёмки:**
- [ ] DnD и кнопка выбора файла работают.
- [ ] Без выбранного типа загрузка невозможна.
- [ ] Успех = файл на месте + сообщение в очереди/exchange.
- [ ] UI не блокируется ожиданием результата парсинга.

### UC-02. Обработка ошибок на стороне UI

**Тип:** новый  
**Актёры:** Оператор, UI  

**Предусловия:** оператор на экране загрузки или повтора уведомления.

**Основной сценарий:**
1. Возникает ошибка (валидация, шара, RMQ, непредвиденная).
2. UI показывает понятное сообщение (без стека в UI).
3. Ошибка пишется в лог с `correlationId` (если уже выделен).
4. Оператор может исправить ввод и повторить действие.

**Альтернативы:**
- **A1. Критическая недоступность инфраструктуры:** экран «Сервис временно недоступен» + код для поддержки.

**Постусловия:** состояние системы согласовано с описанной политикой (нет «тихого» успеха).

**Критерии приёмки:**
- [ ] Для типовых ошибок есть отдельные тексты/коды.
- [ ] В логах есть корреляция для разбора инцидента.

### UC-03. Обработка ошибок по ссылке из письма

**Тип:** новый  
**Актёры:** Оператор, UI, БД, (парсер — вне UI: пишет кейс и письмо)  

**Предусловия:**
- Парсер создал запись `ErrorProcessingCase` + элементы в БД.
- Письмо содержит deep-link вида `/error-processing/{caseId}?token=...` (точный формат — screens/architecture).
- Кейс в статусе, допускающем редактирование (`Pending`), и не истёк `ExpiresAt`.

**Основной сценарий:**
1. Оператор переходит по ссылке из письма.
2. UI проверяет `caseId` + `token`, срок действия, статус.
3. UI читает из БД кейс и проблемные поля/строки.
4. Оператор заполняет/исправляет значения на странице обработки (внешний вид — отдельно).
5. UI валидирует обязательные поля формы.
6. UI сохраняет значения в БД и переводит кейс в `ResolvedByUser`.
7. UI показывает подтверждение успешного сохранения.

**Альтернативы:**
- **A1. Невалидный token / истёк срок / кейс не найден:** UC-04.
- **A2. Кейс уже `ResolvedByUser`:** показать read-only или сообщение «уже обработан».
- **A3. Ошибка сохранения:** транзакция откатывается, оператор видит ошибку, может повторить.

**Постусловия:** данные пользователя в БД; статус `ResolvedByUser`; дальнейший забор — зона парсера.

**Критерии приёмки:**
- [ ] Без валидного token данные кейса недоступны.
- [ ] Сохранение атомарно для кейса и его элементов.
- [ ] Повторное сохранение уже закрытого кейса запрещено или явно определено политикой.

### UC-04. Невалидная или протухшая ссылка

**Тип:** новый  
**Актёры:** Оператор, UI  

**Основной сценарий:**
1. Переход по ссылке с неверным/протухшим token или отсутствующим кейсом.
2. UI показывает понятную страницу отказа (без деталей внутренней модели).
3. Событие логируется (без утечки token в открытые логи целиком — хэш/маскирование).

**Критерии приёмки:**
- [ ] Нет «белого экрана» и нет дампа исключения пользователю.
- [ ] Различие «не найдено» / «истекло» / «уже закрыто» допустимо, если не раскрывает лишнего.

---

### UC-05. Расширение типа списка

**Тип:** новый  
**Актёры:** Администратор данных / разработка  

**Основной сценарий:**
1. В справочник `ListType` добавляется новый активный тип (код, имя, правила пути/routing).
2. Экран загрузки подхватывает тип без изменения кода сценария UC-01 (конфиг/БД).

**Критерии приёмки:**
- [ ] Новый тип появляется в выборе загрузки.
- [ ] Маршрутизация файла/сообщения следует правилам типа.

## 3. Нефункциональные требования

| Область | Требование |
| --- | --- |
| Производительность | Загрузка файла до настраиваемого лимита размера (по умолчанию 50 МБ) без таймаута UI на стороне парсинга |
| Надёжность | Запись файла по возможности атомарна (temp + rename); publish RMQ с retry по политике |
| Безопасность | Token одноразовый/ограниченный по TTL; доступ к шаре и БД по сервисным УЗ; логи без полных PII по возможности |
| Совместимость | Входные форматы: Excel/CSV (белый список расширений) |
| Наблюдаемость | Логирование upload, publish, open error-processing, save error-processing с `correlationId` / `caseId` |
| Аудит | Фиксация кто и когда сохранил обработка ошибок (если известен пользователь) |

## 4. Ограничения и допущения

- Парсер **не предоставляет HTTP API**.
- UI передаёт файл **as is** и **не парсит** содержимое списков (нет OpenXML/CSV-reader и т.п. на стороне UI).
- Визуал страницы обработки ошибок согласуется отдельно; в ТЗ достаточно наличия страницы и сценария.
- Список типов на MVP: как минимум МВК и Террористы; полный перечень — в [list-types.md](list-types.md).
- СУБД: SQL Server, БД `VTBL_Restrict` (см. docs/db).
